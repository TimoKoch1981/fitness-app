## 5. Workflow-Regeln (non-negotiable, aus Sprint-Lehre)

1. **Test-first wo möglich.** Bei Bug-Fixes immer erst einen Reducer-/Component-/
   Source-Lint-Test schreiben, der den Bug reproduziert (rot), dann fixen
   (grün). Vermeidet Wiederholungs-Regressionen. Suffix-Konvention:
   `.failing.test.*` während des Sprints, dann via `git mv` zu `.test.*` umbenennen.

2. **Ein Bug = ein Branch = ein Commit.** Klares Diff, einfach revertbar.
   Konvention: `fix/regression-B<NN>-<slug>` off `develop` oder Integration-Branch.

3. **Bei Multi-Bug-Sprints am Ende EIN Integration-Merge.** Einzelne Fix-Deploys
   überschreiben sich gegenseitig auf dem Server (jeder Branch enthält NUR
   seinen Fix). Erst alle Fix-Branches in den Integration-Branch mergen, dann
   EIN Build + EIN Deploy. (Lehre aus Regression-Sprint 2026-05-17 — Details
   in `feedback_regression_sprint_workflow.md`.)

4. **Memory-System pflegen.** Wenn du etwas Cross-Session-relevantes lernst
   (User-Präferenz, Workflow-Lehre, nicht-offensichtliches Fakt), schreib eine
   Memory-Note. MEMORY.md ist Index (eine Zeile pro Eintrag), separate Files
   für Inhalt.

5. **Keine "Half-Sachen".** Wenn ein Fix komplexer wird als geplant, splitte
   ihn. Lieber eine fertige Portion liefern als drei halbfertige.

6. **Blast-Radius beachten.** Lokale, reversible Aktionen (Edit, Test) sind
   frei. Push, DB-Migration, Force-Push, Deploy, Branch-Delete sind shared-state
   und brauchen kurze Bestätigung — außer Timo hat explizit "mach autonom"
   gesagt für diese Aktion. Niemals `--no-verify`, `--force-with-lease` oder
   `git reset --hard` ohne explizite Bitte.

7. **regression-shield Skill nutzen.** Vor jedem nicht-trivialen Code-Change
   den `regression-shield` Skill triggern (Anti-Regression-Checkliste). Vor
   allem bei: Telemetrie-Wraps, Shared-Infrastruktur (Auth, Validation,
   Error-Handling), UX-Patterns, die woanders schon existieren.

## 8. Typische Aufgaben-Patterns

### Pattern A — Bug-Fix Single-File
1. Bug reproduzieren / Symptom verifizieren
2. Failing-Test schreiben (`.failing.test.*` Suffix)
3. `npx vitest run <test>` → rot bestätigen
4. Fix implementieren (kleinstmöglicher Diff)
5. `npx vitest run <test>` → grün
6. `npx tsc --noEmit` + full suite `npx vitest run`
7. `git mv ...failing.test.* ...test.*`
8. Commit `fix(BX): <kurz>` mit Body (Root-Cause + Fix + Verifikation)
9. Build + Deploy + USER-VERIFIKATION-Block
10. Nach Timo OK → TODO.md update

### Pattern B — Feature
1. Konzept-Doc unter `docs/KONZEPT_<NAME>.md` (Marktanalyse, med./wiss.
   Grundlage falls health-relevant)
2. Migration falls DB-Schema betroffen — Naming `supabase/migrations/YYYYMMDDNNNNNN_<slug>.sql`
3. Types in `src/types/health.ts` (oder fachlich passender Datei)
4. Hooks unter `src/features/<feature>/hooks/`, Components unter `.../components/`
5. i18n-Keys in DE + EN parallel
6. Tests pro Hook + Smoke-Test pro Component
7. Doku-Update: ARCHITEKTUR.md (falls neue Tabelle), TODO.md (gefixed), FORTSCHRITT.md (Log-Eintrag)

### Pattern C — Code-Cleanup / Refactor
- Beachte `regression-shield` Skill — Refactors haben hohes Regressions-Risiko
- Bei großen Sweeps (z. B. Color-Migration): test files vom Sweep ausschließen
  (siehe Sprint v14.28 Stufe 4 für Beispiel)
- Vor & nach Sweep: `npx vitest run` muss identische Counts liefern
